## 一面：基础深挖与算法

### 经历追问

### Go 基础与并发

1. Go 中的 Map 和有序 Map
2. Map 多线程有什么问题，怎么解决（原生 map 并发读写会直接触发 fatal error，无法 recover；可用 sync.RWMutex 封装或使用 sync.Map）
3. sync.Map 怎么实现线程安全，读需要加锁吗（read/dirty 两个 map，读大多走 read map，用 atomic.Value 原子操作，不加锁；read 未命中才加锁查 dirty）
4. 原子操作（CAS）和 Mutex 有什么区别，都用 Mutex 不行吗（CAS 是硬件级乐观锁不阻塞，冲突严重时空耗 CPU；Mutex 让 goroutine 休眠，有上下文切换开销但整体吞吐稳）
5. Go 中怎么保证内存可见性，底层怎么实现（没有 volatile，靠 sync/atomic 或互斥锁；底层涉及主内存与工作内存交互、读写屏障、happens-before；多核下靠 MESI 缓存一致性协议和总线嗅探）

### 项目与场景

- 微服务之间怎么交互，系统并发多少，怎么优化的
- 算法题：给一个 M*N 矩阵，从 1 开始逆时针打印数字，时间复杂度尽可能低（核心是判断什么时候变换方向，按右、下、左、上循环）

## 二面：架构设计与底层原理

### 非技术开场

先自我介绍，问手上还有没有其他 offer，部门组织结构是怎样的。

### 项目深挖与微服务架构（面试官让在纸上画系统模块流转图）

1. 链路追踪的信息是怎么传递的（Go 里主要靠 context.Context 透传，底层把 TraceID、SpanID 塞在 RPC Header 或 gRPC metadata 里）。追问：SpanID 怎么保证唯一性（UUID 或雪花算法）；Context 是在什么维度传递的（goroutine 之间显式传递保持关联）
2. gRPC/KiteX 的远程调用是怎么实现的（从客户端动态代理、拦截器、负载均衡策略、连接池管理，到基于 HTTP/2 的多路复用、Protobuf 序列化，以及服务端注册中心监听和服务发现）
3. Go 的单例是怎么实现的（sync.Once，底层互斥锁加原子标志位，双检查锁机制）
4. 为什么要单独实现一个服务治理框架（内部微服务起步，想做更深度的监控和性能优化）。追问：谁主导的，内部是否还在用，有没有想过做成通用化方案

## 复盘建议

- Go 岗的八股深度明显比"知道概念"深一层：map 并发崩溃的机制、sync.Map 的读写分离、CAS 与 Mutex 的适用边界、内存可见性讲到 MESI。建议每个知识点都备一个"底层怎么实现"的版本。
- 二面全程围着架构图展开，链路追踪是重灾区。Context 透传、Span 结构、TraceID 唯一性这套要能画出来讲，相关准备方法见[项目深挖面试准备清单](../面试攻略/项目深挖面试准备清单.md)。
- 一面算法（矩阵逆时针打印）是模拟方向变换，注意边界判断；先讲清思路再写代码，这轮面试官看重推理过程。
- 分享者手握华为、字节 offer 仍认真准备每一轮，面试里被问"还有没有其他 offer"时如实回答即可，不卑不亢。
